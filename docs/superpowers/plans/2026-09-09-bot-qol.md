# Bot QOL Implementation Plan

**Goal:** Implement all ten approved Telegram QOL improvements without changing Gold bias rules or adding a market-data provider.

**Architecture:** Keep the existing scraper and scheduler. Add pure presentation helpers, a durable QOL service, per-request calendar metadata, and an injectable command controller. Persist notification preferences, alert snapshots/message IDs, deferred alerts and calendar snapshots in the existing lowdb store. All sends remain at-least-once: an ambiguous network timeout cannot guarantee exactly-once Telegram delivery.

**Tech Stack:** Existing Node.js, lowdb, moment-timezone, node-schedule and Telegram Bot API. No new dependencies.

## Approved Behavior

1. `/next`: next full simultaneous group, dated SGT time and countdown; disclose cached calendar age.
2. Link results to warnings and changed actual/previous values to prior results using persisted message IDs. Corrections send new notifications.
3. Each event alert has Why, Source and Mute controls. Explanations use immutable event/context snapshots. Muting is per event occurrence, silent rather than dropping records.
4. `/noise low` enables silent low/non-economic alerts, `/noise normal` restores normal sound. All events remain visible. Preferences apply to the configured notification chat.
5. `/pause 1h` (1m through 24h) persists expiry; fetches continue; deferred results are consolidated into a catch-up report when resumed, including after restart. `/resume` resumes early. Failed catch-up delivery remains queued.
6. All user-facing diagnostic timestamps use SGT and relative times; machine health JSON remains ISO.
7. `/check` acknowledges immediately, uses cached snapshots, shares in-flight refreshes and edits the acknowledgement with fresh results. Register commands before startup network calls.
8. Detect explicit moved/tentative/cancelled records and replace reminders. Never infer cancellation from a missing row, partial response, feed failure or Cloudflare challenge. Retain earlier rows when snapshots are partial. Record source provenance.
9. Results obtained/delivered 5 minutes or more after release are labelled LATE, with release and observation times distinct.
10. `/status` has compact calendar/pending/delivery/notification state; Details expands diagnostics.

## Decisions

- Work in the current IDE checkout on `codex/bot-qol`; do not create another checkout or push.
- Muted events are delivered silently and can be unmuted from the same button. This preserves the user's requirement not to lose events.
- Do not claim price confirmation or a guaranteed trade direction. Why explains only existing release heuristics.
- Retain QOL history for 14 days; retain undelivered deferred alerts until successfully delivered.
- Final verification: `npm test` passed 187 tests, including real-process startup and real Telegram SDK payload checks against localhost fixtures. `git diff --check` passed. The suite requires localhost binding permission for smoke tests. No live provider or Telegram requests were used.
- Review corrections: share normalization for alert/Why; ignore missing cache timestamps; use persisted delivery status in Details; reject outdated result-job timing; preserve observed values on calendar-only fallback; notify corrections even when values revert.
- Final review corrections: reconcile request versions per event; preserve native IDs through feed fallback; collect canonical caches after cross-date refreshes; rebuild schedules after `/check`; respect legacy dedupe and current alert filters; preserve silent delivery and all catch-up controls; recheck each warning after preceding async sends. Scoped reviews found no remaining findings in these fixes.
